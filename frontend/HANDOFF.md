# Website and workspace handoff

What was built on 2026-10-04/05, what it claims, what it deliberately does not claim, and
what the owners still need to supply. Read this with `CONTENT.md` (where every claim
comes from) and `VERIFICATION.md` (how it was checked).

## 1. What this branch contains

- The MVP backend merged from `origin/mvp` (CLI, Runner, deterministic judge, flag-only
  Policy engine, Ed25519 signing, file and Postgres stores, report folder, eleven mock
  agents, test suite). Nothing in `src/` was changed by this work.
- A rebuilt public website in `frontend/` (Next.js 16, static export):
  `/`, `/product`, `/workflows`, `/demo`, `/security`, `/docs`, `/docs/getting-started`,
  `/docs/cli`, `/docs/evidence`, `/company`, `/access`, `/privacy`, `/terms`.
- A review workspace at `/app`: overview, new-evaluation setup, report import, agent
  detail, evaluation detail (summary, tests and evidence, coverage gaps, card,
  execution, signature with in-browser verification, review), comparison, settings.
  It reads the report folders the CLI writes and stores them in the browser only.
- A sample data set (`frontend/lib/sample/`) generated by
  `frontend/scripts/make-sample.py` through the real Suncly code path against a fictional
  local agent: three signed attestations (baseline, regression with an unchanged card,
  budget stop). Regenerate with `.venv/bin/python frontend/scripts/make-sample.py`.
- A design system in `app/globals.css` and `components/ui/`: tokens, badges, cards,
  tables, fields, dialog, tabs, notices, empty states, stats, code blocks, meter.
- Search and answer-engine optimisation: `lib/seo.ts` (brand entity, keyword
  clusters, metadata helper, JSON-LD builders), structured data on every public page,
  a `/glossary` page, `public/llms.txt` and `llms-full.txt`, an AI-crawler-aware
  `robots.txt`, a full sitemap and a web manifest. Strategy, keyword map and the
  off-site checklist are in `SEO.md`.

## 2. Capability map used throughout

`frontend/lib/capabilities.ts` is the single source. Summary:

| Status | Items |
| --- | --- |
| Available | Card fetch and hash; human approval of the contract; repeated runs with run keys; Runner credential isolation and redaction; budget and execution controls; signed evidence and `suncly verify`; "What was NOT tested"; report folder; CLI |
| Available with limits | Deterministic drafter (no model; no examples → not tested); deterministic judge only; customer criteria are structural (`model_checks` → inconclusive); sandbox is a declaration; append-only store (transcripts on local disk); Policy engine flag-only; CI via the CLI; comparison computed in the workspace |
| Planned | Probes (stage 4); Judge Layer 2 (stage 4); recording human decisions in the store (stage 5, OQ-P2); HTTP API (stage 5); CI adapter (stage 5); registry adapters (stage 6); object storage for transcripts |

The site distinguishes behavioural evaluation (what Suncly does), protocol compliance
(checked as part of judging, not a product) and runtime monitoring (not offered,
schema §10).

## 3. Claims withheld, and why

- **"10 supported workflows involving Claude, Grok and Codex."** Not substantiated by
  the implementation. Suncly has no model-provider, framework or coding-tool
  integration; it speaks A2A 1.0 over JSON-RPC and nothing else
  (`docs/IMPLEMENTATION_NOTES.md`, OQ-A4). The only list of ten-or-so things in the
  repository is the eleven bundled mock agents. The site therefore says Suncly is
  model-agnostic through A2A, lists model names only to illustrate that, carries a
  disclaimer that no partnership or endorsement exists, and shows the mock agents as
  what they are. No model or company logos were added: no logo assets exist in the
  repository, the sandbox cannot fetch them, and using third-party marks needs the
  owners' trademark review. Text chips are used instead.
- **Google Cloud and AWS relationship.** No wording, asset or document in the
  repository establishes any relationship. The only mentions are "Google Cloud SQL" as
  one of several Postgres targets in `db/README.md` and a note that creating cloud
  resources needs the founders' accounts. AWS is not mentioned anywhere. Nothing was
  published. See section 5.
- **Customers, testimonials, logos, certifications, benchmark results, evaluation
  counts, time savings, security guarantees.** None exist in the repository; none were
  invented. The manual-review comparison is descriptive, not a measurement.
- **Prices and commercial terms.** None published. `/access` states that access is
  arranged by email and that a payment layer is planned.
- **Legal identity, retention periods, governing law, licence.** Not in the repository.
  `/privacy` and `/terms` are visibly marked as drafts pending owner review, with the
  missing fields marked "to be supplied by the owners". Both pages are `noindex`.
- **"Trusted by".** Not used anywhere.
- **Automatic approve or block.** The Policy engine only produces `flag`; the site
  says so on every page that mentions decisions.
- **Starting runs from the browser, live progress in the browser.** Not possible
  without the HTTP API; the setup page builds the exact CLI commands and describes the
  CLI's live output instead of simulating it.

## 4. Payment readiness

Where a future payment layer connects, and what is undecided:

- **Account.** There is no account or identity system; schema §10 puts identity out
  of scope and OQ-P3 expects an external source for `approved_by` and `decided_by`.
  The workspace's "reviewer identifier" is a local default only. Decision needed: which
  identity provider supplies reviewer identity for the workspace and the API.
- **Usage.** The only usage unit the code counts is attempts per attestation
  (`cost_total` against `budget_limit`, OQ-D1: one attempt costs 1). Decision needed:
  whether billing is per attestation, per attempt, per agent or per seat, and whether
  `cost_total` becomes a billable unit or stays an execution cap.
- **Billing surface.** `/access` (public) and `/app/settings` "Account, usage and
  billing" (workspace) are the two places that state billing is planned. They contain
  no controls. When checkout exists it belongs on `/access` (public plans) and in
  settings (workspace billing), with the capability map updated from `planned`.
- **Conflict to resolve.** `SCHEMA.md` §10 lists payments as out of scope for the
  product; the brief says a payment layer is next. The website treats payments as a
  commercial layer outside the core, but the schema should say so explicitly before
  billing is built.
- **Data.** Payment details must never pass through the static site; the pilot form
  posts only an email and a note (to `NEXT_PUBLIC_SIGNUP_ENDPOINT`, or mailto when
  unset).

## 6. Known limitations of this delivery

- The workspace cannot start runs, poll progress or record decisions into the
  evidence store; all three need the stage 5 API. It reads report folders, verifies
  them, compares them and exports reviewer notes.
- Report folders are imported by file selection; the evidence store itself (files
  under `~/.suncly` or Postgres) is not read by the browser.
- Sample timestamps are real generation times (all on 2026-10-04), minutes apart,
  because the Runner uses the system clock and the signatures cover the transcripts.
- Lighthouse mobile performance on the home page is 88 (desktop 100); the remaining
  cost is hydration JavaScript for the interactive sections.
- The old marketing sections (architecture, roadmap, interfaces, open standard,
  terminal) were removed; their facts now live on `/product`, `/workflows`,
  `/security` and the docs pages.

## 7. Demo journey for the marketing video

Stable fictional data, all on the sample set; every screen is a real page.

1. **Connect an agent** — `/app/new`: enter
   `https://sandbox.harbor.example/.well-known/agent-card.json`, tick the sandbox
   declaration, set owner and medium risk, name the approver; the command assembles on
   the right.
2. **Review tests** — `/app/evaluation?id=<evaluation 2>&tab=tests`: select
   `start-return` to see the approved criteria (expected `TASK_STATE_COMPLETED`,
   2000 ms, text/plain, required answer text).
3. **Run evaluation** — the terminal: `suncly attest … --sandbox --approve-as …`
   (the live progress lines come from the CLI; record the terminal, not the browser).
4. **Discover a failure** — `/app` overview: "Awaiting human review 2", "What changed:
   card unchanged, 2 regressed"; open evaluation 2: `start-return` 0 pass / 5 fail,
   "Inconsistent behaviour on 1 test case".
5. **Inspect evidence** — Tests and evidence tab, open a `start-return` run: Final task
   state expected `TASK_STATE_COMPLETED`, observed `TASK_STATE_INPUT_REQUIRED`, the
   agent's question in the final response, the redacted exchange; Signature tab, "Run
   verification": eight checks pass.
6. **Make an approval decision** — Review tab: the automated recommendation (flag),
   then record "Block" with the rationale, export the note; Compare page: evaluation 1
   versus 2, "Card unchanged", `start-return` regressed.

To reset between takes: `/app/settings` → Clear the workspace → `/demo` → Load sample
into workspace.
